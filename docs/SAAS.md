# نسخهٔ فروش سینا (SaaS) — معماری، مدل کسب‌وکار و راهنمای عملیات

> همان کدبیس سینا AI OS، با یک لایهٔ چند‌مستأجری روی آن. اکانت شخصی شما هم اکنون
> «مستأجر شمارهٔ ۱» با پلن کسب‌وکار است و پنل مدیریت پلتفرم را در اختیار دارد.

---

## ۱. چه چیزی فروخته می‌شود؟

یک **عامل هوشمند اجرایی** که هر مشتری حساب، فضای‌کار و کلیدهای خودش را دارد و می‌تواند:

| قابلیت | ابزار عامل | نمونه دستور |
|---|---|---|
| ورود به سرور مشتری | `ssh` (exec/upload/download/service) | «روی سرورم nginx را ری‌استارت کن و لاگ خطا را بفرست» |
| مدیریت دامنه | `cloudflare` (DNS CRUD + purge) | «ساب‌دامین app برای 1.2.3.4 بساز» |
| کد و ریپازیتوری | `github` (repo/file/issue/PR) | «باگ #12 را در برنچ جدید فیکس کن و PR بزن» |
| پیام‌رسانی | `telegram` (ربات خود مشتری) | «گزارش فروش امروز را به کانال بفرست» |
| کد و محاسبه | `python_exec`, `terminal`, `files` | «این CSV را تحلیل کن و نمودار بساز» |
| وب | `web_search`, `web_fetch`, `browser` | «قیمت رقبا را جمع کن و مقایسه بده» |
| حافظه | `pgvector` | «مثل همیشه گزارش را فارسی و کوتاه بده» |

مدل درخواست مشتری است: هر مشتری **کلیدهای خودش** را وصل می‌کند؛ هیچ کلید مشترکی
بین مشتری‌ها وجود ندارد.

## ۲. چرا امن است؟ (محدودیت‌هایی که عمداً گذاشته شده)

1. **جداسازی کلیدها**: هر اتصال با `user_id` مالک ذخیره می‌شود؛ عاملِ یک مشتری فقط
   کلیدهای همان مشتری را می‌بیند (`_config(ctx.user_id, kind)`).
2. **رمزنگاری در حال سکون**: کلیدها با Fernet رمزنگاری می‌شوند؛ در API فقط
   `••••••` برمی‌گردد؛ هرگز به مدل زبانی فرستاده نمی‌شود.
3. **دروازهٔ تأیید**: هر عملی که سیستم خارجی را تغییر می‌دهد (SSH، DNS، کامیت،
   ارسال پیام) `risk=confirm` است و تا تأیید انسان اجرا نمی‌شود.
4. **محدودیت میزبان**: در اتصال SSH فیلد `allowed_hosts` وجود دارد؛ اگر پر شود
   عامل فقط به همان میزبان‌ها وصل می‌شود.
5. **سهمیه و جداسازی داده**: هر کار به `user_id`/`tenant_id` بسته است؛ لیست‌ها
   همیشه فیلتر می‌شوند. تست `test_credentials_are_private_per_tenant` این را تضمین می‌کند.
6. **محدودیت نرخ**: ثبت‌نام ۵ در دقیقه از هر IP، لاگین ۱۰ در دقیقه.
7. **حساب تعلیق‌شده** نمی‌تواند کار جدید بسازد (`403`).

> صادقانه: اجرای کد مشتری در همان کانتینر ورکر انجام می‌شود (بدون سوکت داکر).
> برای جداسازی سخت‌تر در مقیاس بزرگ، هر مستأجر را در worker/container جداگانه
> بگذارید — مسیر توسعه در بخش ۷ آمده است.

## ۳. پلن‌ها و قیمت (منبع حقیقت: `backend/app/plans.py`)

| پلن | قیمت ماهانه | کار/روز | توکن/ماه | فضای‌کار | اتصال |
|---|---|---|---|---|---|
| رایگان | ۰ | ۱۰ | ۴۰۰هزار | ۲ | ۲ |
| حرفه‌ای | ۸۹۰٬۰۰۰ تومان | ۱۵۰ | ۶میلیون | ۱۵ | ۱۲ |
| کسب‌وکار | ۲٬۴۰۰٬۰۰۰ تومان | ۸۰۰ | ۳۰میلیون | ۶۰ | ۶۰ |

- دورهٔ آزمایشی: ۷ روز با سهمیهٔ پلن حرفه‌ای (`SIGNUP_TRIAL_DAYS`).
- سالانه = ۱۰ برابر ماهانه (۲ ماه هدیه).
- تغییر قیمت/سهمیه فقط با ویرایش `plans.py` و ری‌استارت api؛ فرانت از API می‌خواند.

## ۴. چرخهٔ فروش (همه از پنل، بدون کدنویسی)

```
مشتری → لندینگ / → ثبت‌نام (/signup) → دورهٔ ۷ روزهٔ حرفه‌ای
        ↓
   داشبورد → اتصال کلیدها (/integrations) → اولین کار (/chat)
        ↓
   تمام‌شدن سهمیه → /subscription → «ثبت درخواست ارتقا» + شمارهٔ پیاری واریز
        ↓
   شما: /admin → تب درخواست‌ها → تأیید  →  پلن فوراً فعال می‌شود
```

- **تعلیق مشتری**: `/admin` → تب مشتری‌ها → «تعلیق» (دلیل هم ثبت می‌شود).
- **تمدید آزمایشی**: دکمهٔ «+۷ روز».
- **تغییر پلن دستی**: منوی کشویی پلن در همان جدول.
- **درآمد ماه**: کارت «درآمد تأییدشدهٔ این ماه» از جمع درخواست‌های تأییدشده.

## ۵. راه‌اندازی و تنظیمات

```bash
# .env روی سرور
PLATFORM_ADMIN_EMAILS=admin@sina.local     # ایمیل‌های مدیر پلتفرم (کاما)
SIGNUP_ENABLED=true
SIGNUP_TRIAL_DAYS=7
SALES_BRAND=سینا کلود
SUPPORT_TELEGRAM=your_support_id
SUPPORT_EMAIL=support@example.com
```

- **مهاجرت دیتابیس**: `docker compose exec api alembic upgrade head`
  (ریویژن `b2c3d4e5f6a7` — جدول‌های `tenants` و `plan_requests` + ستون `users.tenant_id`).
- **پشتیبان‌گیری**: قبل از هر مهاجرت `deploy/scripts/backup.sh`.
- **دسترسی ادمین**: کاربری که ایمیلش در `PLATFORM_ADMIN_EMAILS` باشد، در
  `/auth/me` مقدار `platform_admin: true` می‌گیرد و لینک پنل در سایدبار ظاهر می‌شود.

## ۶. API نسخهٔ فروش

| متد | مسیر | توضیح |
|---|---|---|
| GET | `/api/public/meta` | پلن‌ها، برند، آمار لندینگ |
| POST | `/api/public/signup` | ساخت مستأجر + کاربر + توکن |
| POST | `/api/public/contact` | ثبت سرنخ فروش (در audit) |
| GET | `/api/billing/me` | پلن، مصرف، درخواست‌ها، کاتالوگ |
| POST | `/api/billing/request` | درخواست ارتقا/تمدید |
| GET | `/api/admin/overview` | آمار پلتفرم (مدیر) |
| GET | `/api/admin/tenants` · `PATCH /{id}` | مدیریت مشتری‌ها |
| GET | `/api/admin/requests` · `POST /{id}/decide` | تأیید/رد پرداخت |
| GET | `/api/admin/audit` | رخدادهای پلتفرم |

## ۷. مسیر توسعهٔ بعدی (شفاف — هنوز پیاده نشده)

- درگاه پرداخت آنلاین (زرین‌پال/آیدی‌پی) به‌جای تأیید دستی.
- ایمیل تراکنشی (خوش‌آمد، یادآوری پایان دوره).
- فاکتور PDF و مالیات.
- جداسازی worker به ازای هر مستأجر برای مقیاس بالا.
- نقش‌های تیمی داخل یک مستأجر (الان هر مستأجر یک مالک دارد).
