# امنیت Sina AI OS

اصل حاکم: **اجرای خودمختار ≠ اجرای بی‌محدودیت.** سطح دسترسی عامل، حداقلِ لازم برای انجام کار است.

## ۱. مدل تهدید

| مهاجم | سطح دسترسی فرضی | هدف |
|---|---|---|
| کاربر اینترنت | بدون توکن | نفوذ به API/داشبورد |
| کاربر مجاز تلگرام (ناشناس) | توکن ربات | سوءاستفاده از عامل |
| محتوای وب / فایل آپلودی | ورودی داده | prompt injection برای اجرای دستور ناخواسته |
| مدل زبانی نادرست | تولید tool-call | عملیات مخرب روی میزبان |
| دسترسی محلی به کانتینر | RCE در سندباکس | فرار از کانتینر / دسترسی به میزبان |

## ۲. کنترل‌های پیاده‌شده

### ۲.۱ احراز هویت و مجوز
* JWT امضاشده (HS256) با `jti` و جدول `sessions` → **ابطال سرورساید** در logout/انقضا.
* هش رمز با **scrypt** (stdlib، پارامترهای n=2^14, r=8, p=1) — بدون وابستگی خارجی.
* نقش‌ها: `owner/admin/member/viewer`؛ عملیات حساس (تغییر مدل‌ها) فقط owner/admin (`require_roles`).
* محدودیت نرخ روی ورود (۱۰ در دقیقه بر IP) و مسیرهای API.

### ۲.۲ ابزارها و سیاست اجرا
سه لایه:
1. **طبقه‌بندی ریسک** (`classify_command`): `safe` / `confirm` / `admin` / `blocked`.
   * blocked: `sudo`, `mkfs`, `dd of=/dev/*`, `shutdown/reboot`, `iptables/nft/ufw`, `rm -rf /`, `curl|sh`, `docker --privileged`, fork-bomb، اشاره به `docker.sock`.
   * admin: `systemctl`, `apt install/remove`, `npm -g`, `crontab`, `git push --force`، نصب pip خارج از allow-list.
   * confirm: `rm -`, `git push`, `docker rm/stop`, `kill`, `ssh`, `nc/socat`.
2. **دروازهٔ تأیید**: هر فراخوانی با ریسک `confirm`/`admin` (طبق `REQUIRE_APPROVAL_LEVELS`) اجرا **متوقف** می‌شود؛ رکورد `approvals` ساخته و وضعیت کار `waiting_approval` می‌شود؛ تأیید/رد از داشبورد یا تلگرام.
3. **سندباکس**: `EXEC_MODE=local` → اجرا داخل کانتینر ورکر (کاربر غیر root، بدون دسترسی به داکر). `EXEC_MODE=docker` → هر دستور در کانتینر موقت با `--network none`, `--read-only`, `--cap-drop ALL`, `--no-new-privileges`, محدودیت `memory/cpus/pids`, `--user 1000:1000`, mount فقط فضای‌کار.

### ۲.۳ فایل و مسیر
* `safe_join` همهٔ مسیرها را `resolve` می‌کند، مسیر مطلق و NUL را رد می‌کند و بررسی می‌کند که مسیر نهایی زیر ریشهٔ فضای‌کار باشد (ضد path traversal و symlink escape).
* نام فایل آپلود با `Path(name).name` پاک‌سازی می‌شود؛ سقف حجم (`MAX_UPLOAD_MB`).
* حذف ریشهٔ فضای‌کار ممنوع است.

### ۲.۴ اسرار
* کلیدها فقط از ENV (`.env` که در `.gitignore` است).
* اسرار یکپارچه‌سازی‌ها با **Fernet** رمزنگاری و ذخیره می‌شوند؛ API فقط «فیلدهای پیکربندی‌شده» را برمی‌گرداند، نه مقدار را (تست خودکار دارد).
* `sanitize_output` الگوهای رایج کلید (`sk-`, `ghp_`, `token=`, `Bearer`) را در خروجی ابزارها/لاگ‌ها حذف می‌کند.

### ۲.۵ prompt injection
پرامپت سیستم صریحاً می‌گوید محتوای وب/اسناد/ابزار «داده» است نه دستور. علاوه بر آن، حتی اگر مدل فریب بخورد، ابزارهای پرخطر پشت دروازهٔ تأیید انسانی هستند و دستورهای مخرب در لایهٔ `classify_command` مسدود می‌شوند (دفاع چندلایه، نه فقط تکیه بر پرامپت).

### ۲.۶ عملیات و پایش
* `audit_logs` برای ورود/خروج، ساخت و لغو کار، تصمیم تأیید، تغییر تنظیمات و یکپارچه‌سازی‌ها.
* لاگ ساختاریافته JSON روی stdout؛ هیچ مقدار حساسی لاگ نمی‌شود.
* هشدار در بوت برای اکانت seed شده.

## ۳. چک‌لیست استقرار امن (Production)

- [ ] `JWT_SECRET` تصادفی ۳۲ بایتی و `SECRETS_ENCRYPTION_KEY` تولیدشده با Fernet
- [ ] `ADMIN_PASSWORD` قوی و یکتا؛ بلافاصله پس از اولین ورود تغییر داده شود
- [ ] `CORS_ORIGINS` محدود به دامنهٔ واقعی
- [ ] پورت‌های ۸۰۰۰/۳۰۰۰ فقط روی `127.0.0.1` (در Compose همین‌طور است)
- [ ] TLS در nginx؛ HSTS؛ محدودیت نرخ در لبه
- [ ] `TELEGRAM_ALLOWED_IDS` فقط شناسه‌های خودتان
- [ ] بکاپ زمان‌بندی‌شده (`deploy/scripts/backup.sh` در cron)
- [ ] بررسی دوره‌ای `audit_logs` و `/system/stats`
- [ ] `EXEC_MODE=docker` برای اجرای کد نامعتمد (در ورکر: بدون mount سوکت داکر؛ فقط socket-proxy محدود)

## ۴. محدودیت‌های شناخته‌شده (صادقانه)

1. **لاگ ممیزی در همان دیتابیس** است؛ در صورت نفوذ کامل به دیتابیس قابل دستکاری است. توصیه: ارسال لاگ به سیستم خارجی (Loki/S3) در استقرار حساس.
2. **محدودیت نرخ درون‌فرآیندی** است (به ازای هر replica). برای چند replica از Redis-based limiter استفاده کنید.
3. `sanitize_output` بهترین تلاش است؛ ضمانت قطعی برای هر الگوی ناشناخته نیست.
4. `web_fetch` HTML را بدون اجرای JS استخراج می‌کند (SSRF به شبکهٔ داخلی مسدود نشده — در استقرار حساس، allow-list دامنه اضافه کنید).
5. سندباکس Docker نیازمند دسترسی ورکر به داکر است؛ راه امن پیشنهادی: **socket-proxy** با مجوز فقط `CONTAINERS=1` و `POST=1` (نه mount مستقیم `docker.sock`).
